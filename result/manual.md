# Частина I. Вступ

## 1. Про що цей посібник

`wikipedia-trend-agent` — навичка (Agent Skill), яка відповідає на запити про
**зростання інтересу до тем і мовних розділів Wikipedia** за даними Wikimedia
Pageviews API.

Механіка в одному реченні: **ви пишете один файл `spec.json`, запускаєте одну
команду і читаєте один файл `metrics.json` плюс звіт на одну сторінку з
графіками.**

### Що навичка робить

| Запит | Результат |
|---|---|
| «Чи зростає інтерес до теми X?» | одна серія, вікна 3M/1Y/2Y, напрям тренду, рівень впевненості |
| «Порівняй інтерес у польській і чеській Wikipedia» | дві+ серії, окремі графіки + `chart_overlay.png` зі співставленням |
| «Наскільки можна довіряти цьому тренду?» | `confidence`, `confidence_reasons`, список `anomalies` |
| «Який розділ розвивати наступним?» | порівняння `clean` зростання між мовними розділами |

### Чого навичка не робить

- **Не прогнозує.** Усі числа описують вже завершені дні минулого вікна.
- **Не вимірює попит і здатність платити.** Перегляди статті — це увага до
  статті, а не клієнти, виручка чи намір купити.
- **Не пише у Вікіпедію.** Читає лише публічні агреговані лічильники й
  пошукову метадану; бот-політика не застосовується, бо запису немає.
- **Не потребує API-ключів, акаунта чи токенів.**

Кожен згенерований звіт закінчується рядком `Це не прогноз і не рекомендація.` —
це частина замороженого контракту, а не стиль редакції.

### Розділення праці

| Задача | Хто виконує |
|---|---|
| Зрозуміти запит, знайти статтю, поставити уточнювальне питання | агент / ви |
| Завантажити, порахувати зростання, знайти аномалії, побудувати графіки, зверстати звіт | код |
| Скласти відповідь, додавши чесні застереження | агент / ви |

Арифметика повністю в коді. Відповідь **цитує** числа, а не перераховує їх.
Правило ANAL-06 забороняє перераховувати або перетворювати будь-яке значення
нижче за стадією, яка його опублікувала, і це перевіряється автоматично
(розділ 23).

## 2. Як влаштований процес

```
запит користувача
      ↓
resolve_articles.py   (2 запуски: discovery → confirm)   → out/resolved.json
      ↓  spec.json пишеться на основі підтверджень
run_all.py --spec out/spec.json --out out
      ↓
 fetch → analyze → charts → report
      ↓
out/metrics.json + out/report.md + out/charts.json + PNG-графіки
      ↓
відповідь (усі числа цитуються, не вираховуються)
```

### Хто що пише

| Крок | Хто | Що пише у `out/` |
|---|---|---|
| 1 | ви | `spec.json` |
| 2 | `resolve_articles.py` | `resolved.json` |
| 3 | `run_all.py` | `series.csv`, `metrics.json`, `charts.json`, `chart_*.png`, `report.md`, `report.manifest.json` |
| 4 | ви / агент | `answer.md` (відповідь, яку перевіряєте валідатором) |

Ключова властивість: кожна стадія читає **файл-артефакт**, а не стан попередника
в пам'яті. Тому стадію можна перезапустити окремо з іншими опціями, а контракт
між стадіями — це зміст файлів, а не домовленість усередині коду.

### Розкриття за розміром

`resolve_articles.py` **не входить** у `run_all.py`. Це підтверджуваний людиною
крок, який виконується **до** написання `spec.json`: спершу треба побачити докази
(які статті взагалі існують, скільки вони мають переглядів), і лише потім
записувати конкретні слаги.

## 3. Системні вимоги

| Вимога | Значення |
|---|---|
| Python | **≥ 3.11** (3.10 — EOL) |
| Рантайм-залежності | одна: `matplotlib>=3.11` |
| Мережа | HTTPS-доступ до `wikimedia.org` |
| Диск | кілька МБ на кеш `.cache/` |
| ОС | будь-яка, де працює matplotlib; headless не потрібен (backend `Agg`) |

Решта — HTTP, кеш, CSV, статистика, сезонність — реалізована на стандартній
бібліотеці Python. Це і є причина, чому навичка запускається всередині
довільного агентного рантайму без кроків резолву: `urllib.request` замість
`requests`, `csv`/`statistics`/`fractions` замість `pandas`.

Арифметика всередині пайплайну рахується на точних раціональних числах
(`fractions.Fraction`); `float` з'являється лише на межі серіалізації, де
відсоток округлюється один раз до десяткового. Тому `+16.7%` у звіті — це
обчислене без втрати точності й округлене один раз число, а не «приблизно».

# Частина II. Встановлення

## 4. Встановлення залежностей

Перейдіть у каталог навички:

```bash
cd wikipedia-trend-agent
pip install -r requirements.txt
```

`requirements.txt` містить рівно один рядок:

```
matplotlib>=3.11
```

Нижня межа — не точний пін: навичка живе у середовищах, де вже може бути
новіша версія matplotlib, і точний пін створював би конфлікт замість того, щоб
його уникати.

Перевірка, що все встановилося:

```bash
python -c "import matplotlib; print(matplotlib.__version__)"
```

Якщо версія надрукувалася — залежностей достатньо. Жодних інших пакетів
встановлювати не потрібно: ні `pandas`, ні `requests`, ні `numpy` (numpy приходить
транзитивно з matplotlib, але сам код навички його не імпортує).

> **Розділення на runtime і dev.** `pytest`, `ruff` і `mypy` — це інструменти
> розробника, а не користувача. Вони не потрібні для роботи навички.

## 5. Куди покласти навичку

Навичка — це **каталог**, а не Python-пакет. Скопіюйте або склонуйте
`wikipedia-trend-agent/` у теку, де ваш агент шукає навички.

## 6. `WTI_USER_AGENT`

**Обов'язково задайте `WTI_USER_AGENT` до будь-якого мережевого виклику.**
Wikimedia повертає HTTP 403 клієнтам без описової ідентифікації.

```bash
# bash / zsh
export WTI_USER_AGENT="wikipedia-trend-agent/0.1.0 (you@yourdomain.tld) python-urllib"

# PowerShell
$env:WTI_USER_AGENT = "wikipedia-trend-agent/0.1.0 (you@yourdomain.tld) python-urllib"

# cmd.exe
set WTI_USER_AGENT=wikipedia-trend-agent/0.1.0 (you@yourdomain.tld) python-urllib
```

Формат: продукт, версія, **справжня контактна адреса**, транспорт. Максимум
256 кодових точок.

Обмеження, які перевіряються **до** будь-якого запиту:

- значення не порожнє і не складається лише з пробілів;
- немає керуючих символів;
- довжина ≤ 256 кодових точок;
- **це не placeholder** — будь-яке значення, що містить `contact` або
  `example.org`, відхиляється.

Placeholder-ідентифікація не може потрапити в мережу: перевірка відбувається
до випуску запиту, а відмова — це `SystemExit` з actionable-повідомленням.
Помилка з'явиться на stderr разом із кодом виходу, і `run_all.py` додасть рядок
`run_all: stage fetch failed: exited 1`, який називає стадію.

Ставте **свою** адресу. Якщо публікувати особисту не хочеться — використайте
контактний аліас, адресу форми або контрольовану вами розсилку. Не комітьте
особисту адресу, яку не збиралися публікувати.

## 7. Перший запуск-тест

У каталозі навички вже лежить готовий приклад `spec.json`, який використовувався
для регресійних тестів. Запустіть його:

```bash
export WTI_USER_AGENT="wikipedia-trend-agent/0.1.0 (you@yourdomain.tld) python-urllib"
python scripts/run_all.py --spec assets/example.intermittent-fasting.json --out out
```

Очікуваний результат — рядок у stdout:

```
run_all: pipeline complete; output directory: out
```

і код виходу `0`. У `out/` з'являться:

```
out/series.csv
out/metrics.json
out/charts.json
out/chart_pl-post-przerywany_timeseries.png
out/chart_pl-post-przerywany_growth.png
out/chart_cs-pust-prerusovany_timeseries.png
out/chart_cs-pust-prerusovany_growth.png
out/chart_overlay.png
out/report.md
out/report.manifest.json
```

Відкрийте `out/report.md` — це звіт на одну сторінку українською. Якщо він
відкрився, навичка встановлена й працює; далі можна переходити до власних
запитів.

> **Що показує цей приклад.** Обидві серії в ньому дають `low` confidence, і це
> **правильна відповідь**, а не збій. Розділ 21 пояснює, чому саме так і що з
> цим робити.

# Частина III. Робочий процес — 8 кроків

## 8. Крок 1. Сформулювати запит

Вам не потрібно перекладати запит у поля — це робить агент. Вам потрібно
вирішити дві речі:

**1. Яка тема і які мовні розділи.**

| Питання | Приклад відповіді |
|---|---|
| Мовні розділи | польський і чеський → `pl.wikipedia`, `cs.wikipedia` |
| Одна тема чи різні | одна тема в різних розділах (порівняння) або різні теми в одному розділі |
| Період | останній рік, два роки, три роки |

**2. Що робити, якщо тема має різні назви в різних мовах.**

Наприклад, запит про інтервальне голодування. У `cs.wikipedia` є стаття
`Přerušovaný půst` — дослівно про інтервальне голодування. У `pl.wikipedia`
**такої статті немає взагалі**: пошук за `post przerywany`,
`głodzenie przerywane`, `głodówka przerywana`, `przerywany`, `16:8` не дає
відповідного заголовка, а Action API повідомляє `missing` для
`Post_przerywany`, `Głodzenie_przerywane`, `Głodówka_przerywana`,
`Post_przerywany_(dieta)`. Найближча наявна стаття — `Głodówka lecznicza`
(«лікувальне голодування»), і вона описує голодування загалом.

Тому в `--topic` ставиться спільна тема, а для конкретного розділу додається
`--topic-for PROJECT=QUERY` з тим запитом, який має шанс знайти те, що реально
існує. Про механіку — крок 2.

**Межі запиту.** Якщо питання звучить «який ринок вигідніший», навичка не
відповість на це. Вона вимірює увагу до статті. Завжди кажіть вголос, що
інтерес до статті — це не попит і не здатність платити.

## 9. Крок 2. Пошук статей (відкритий запуск)

Перший запуск `resolve_articles.py` йде в мережу і збирає **докази**: які
статті знайшов пошук, які з них реально існують, і скільки переглядів вони
мають за останні 30 повних днів.

```bash
python scripts/resolve_articles.py \
  --topic "intermittent fasting" \
  --projects pl.wikipedia --projects cs.wikipedia \
  --topic-for pl.wikipedia="głodówka przerywana" \
  --out out/resolved.json --ttl-hours 24
```

### Прапорці

| Прапор | Обов'язковий | Що робить |
|---|---|---|
| `--topic "..."` | так | спільна тема природною мовою |
| `--projects CODE` | так, повторюваний | мовні розділи **в порядку**; максимум 8 |
| `--topic-for PROJECT=QUERY` | ні, повторюваний | окремий пошуковий запит для конкретного розділу |
| `--out PATH` | ні | шлях до маніфесту, за замовчуванням `out/resolved.json` |
| `--ttl-hours N` | ні | свіжість кешу; `0` примусово робить запит |
| `--reason "..."` | за умови | обов'язковий для `ambiguous`-проєкту на другому запуску; не більше 256 code points |
| `--select PROJECT=ARTICLE` | на другому запуску | підтвердження вибору; повторюваний |
| `--verbose` | ні | лише діагностичні логи; не змінює результат |

### Що всередині

Для кожного проєкту резолвер робить послідовно (у порядку `--projects`,
приблизно один запит на секунду):

| Крок | Запит | Мета |
|---|---|---|
| 1 | пошук Action API, до 5 кандидатів, тільки namespace 0 | знайти заголовки-кандидати |
| 2 | батч `redirects` + `pageprops` | канонічні назви, ланцюги редіректів, прапорці disambiguation |
| 3 | AQS per-article за 30 днів | чи є у статті взагалі якийсь обсяг |

Пошук свідомо **не звужується** параметром `srwhat` — це дає гірші
результати. Якщо пошук повернув нуль хітів, проєкт одразу стає `unresolved` і
пошук припиняється.

Результат записується в `out/resolved.json` зі статусом
`awaiting_confirmation` і кодом виходу `0`. **Код `0` тут означає «докази
зібрані, чекає на вашого підтвердження», а не «усе знайдено».**

## 10. Крок 3. Читання `resolved.json`

Відкрийте `out/resolved.json` і подивіться на верхній рівень:

```json
{
  "contract_version": "resolved.v1",
  "run_mode": "discover",
  "status": "awaiting_confirmation",
  "topic": "intermittent fasting",
  "topic_overrides": [ { "project": "pl.wikipedia", "query": "głodówka przerywana" } ],
  "generated_at": "2026-09-26T09:15:22+00:00",
  "volume_window": { "start": "2026-08-27", "end": "2026-09-25", "days": 30, "access": "all-access", "agent": "user", "granularity": "daily" },
  "projects": [ ... ]
}
```

**Другий запуск ще не відбувався.** Подивіться на масив `projects` — у ньому
по одному запису на кожен `--projects`, у тому самому порядку.

### Статус проєкту

| `status` | Що означає | Ваша дія |
|---|---|---|
| `ready` | рівно один придатний кандидат, `recommendation` заповнено | підтвердьте `recommendation` |
| `ambiguous` | кілька придатних кандидатів, `recommendation` = `null` | оберите самі і додайте `--reason` |
| `unresolved` | придатних кандидатів немає | роздивіться `reason` нижче, переформулюйте запит |
| `error` | помилка мережі або API | прочитайте `error.code` / `error.message` |

### Доказ, на який дивитися

| Поле | Що дає |
|---|---|
| `search_hits` | усе, що знайшов пошук, у порядку релевантності; `rank` дорівнює позиції |
| `candidates` | що з цього реально є: канонічна назва, ланцюг редіректів, `exact_title_match`, `disambiguation` |
| `candidates[].volume` | `total_views` за 30 днів і `low_volume` (< 1000) |
| `recommendation` | підказка резолвера, **не** вибір |
| `reason` | чому проєкт не розв'язано (див. таблицю нижче) |

**Ранг пошуку — це не підтвердження.** Перший результат пошуку не означає, що
це та стаття, яку мали на увазі. Дивіться `exact_title_match` (істина лише
тоді, коли нормалізоване ім'я запиту точно дорівнює фінальній назві **і**
ланцюг редіректів порожній) і `recommendation`.

### Чому проєкт `unresolved`

| Причина | Що це означає |
|---|---|
| `search_no_hits` | пошук не знайшов нічого (список `search_hits` порожній) |
| `no_selectable_candidates` | кандидати є, але жоден не придатний; у кожного — власна причина |
| `redirect_cycle` | редіректи утворили петлю A→B→A |
| `redirect_too_deep` | ланцюг редіректів довший за 10 хопів |
| `missing_target` | сторінки не існує |
| `non_article_namespace` | це не стаття: категорія, шаблон, Portal: тощо |
| `disambiguation_page` | сторінка розмежування — виміряти її не можна |

Кандидат зі статусом `unresolved` **не видаляється** — зберігається з доказом
(`input_titles`, `redirect_chain`, `namespace`). Це навмисно: у `resolved.json`
видно, *чому* конкретна стаття не підійшла, і ви можете переказати це
користувачу замість мовчання.

**Нуль хітів — не підтвердження.** Проєкт, у якому пошук нічого не знайшов
або який структурно не розв'язаний, підтвердити неможливо. Спроба підтвердити
такий проєкт поверне exit `2`.

### `low_volume` — мітка, а не заборона

Якщо `volume.total_views` менший за 1000 за 30 днів, резолвер ставить
`low_volume: true`, але **кандидат залишається придатним до підтвердження**.
Агент не забороняє вимірювати малопопулярну статтю — він її позначає. Це
різниця між «у нас такі дані» і «ми вирішили замість вас».

Якщо AQS відповів 404, обсяг буде `status: "unavailable"` з
`total_views: null` і причиною `aqs_404_zero_or_not_loaded` — **ніколи не `0`**.
Нуль читається як вимірювання; насправді виміряти було неможливо.

### Добрий і поганий запис

Добрий — є, що підтверджувати:

```json
{
  "project": "pl.wikipedia",
  "effective_query": "głodówka przerywana",
  "query_source": "project_override",
  "status": "ready",
  "recommendation": "G%C5%82od%C3%B3wka_lecznicza",
  "search_hits": [ { "title": "Głodówka przerywana", "rank": 1 }, ... ],
  "candidates": [
    { "status": "selectable", "article": "G%C5%82od%C3%B3wka_lecznicza",
      "title": "Głodówka lecznicza", "namespace": 0, "exact_title_match": false,
      "disambiguation": false,
      "volume": { "status": "available", "total_views": 5814,
                  "observed_days": 30, "low_volume": true, "reason": null } },
    { "status": "unresolved", "article": null, "title": "Post przerywany",
      "reason": "missing_target", "redirect_chain": [] }
  ],
  "selection": null, "reason": null, "error": null
}
```

Поганий — немає чого підтверджувати:

```json
{
  "project": "cs.wikipedia",
  "effective_query": "intermittent fasting",
  "status": "unresolved",
  "recommendation": null,
  "search_hits": [],
  "candidates": [],
  "selection": null,
  "reason": "search_no_hits", "error": null
}
```

У такому разі не пишіть `spec.json` з вигаданим слагом. Змініть `--topic` або
`--topic-for` для цього розділу і повторіть крок 2.

## 11. Крок 4. Офлайн-підтвердження

Другий запуск **не робить жодного мережевого запиту**. Наявність `--select`
перемикає режим у `confirm` — автовиявлення немає.

```bash
python scripts/resolve_articles.py \
  --topic "intermittent fasting" \
  --projects pl.wikipedia --projects cs.wikipedia \
  --topic-for pl.wikipedia="głodówka przerywana" \
  --out out/resolved.json \
  --select pl.wikipedia=G%C5%82od%C3%B3wka_lecznicza \
  --select cs.wikipedia=P%C5%99eru%C5%A1ovan%C3%BD_p%C5%AFst
```

### Обов'язкові правила другого запуску

1. **Повторіть `--topic`, порядок `--projects` і кожен `--topic-for` точно.**
   Зміна або пропуск будь-якої умови → exit `2`, а попередній маніфест
   discovery **зберігається недоторканим**. Це навмисно: підтвердження має
   стосуватися тих самих умов, за яких зібрані докази.
2. **Один `--select` рівно на кожен запитаний проєкт.** Більше або менше —
   відмова.
3. **Значення `--select` беріться дослівно з `candidate.article`.** Це
   percent-encoded форма (`quote(title, safe="")`), а не те, що ви пам'ятаєте.
4. **Для `ambiguous`-проєкту додайте `--reason`.** Причина — це запис
   людського рішення, тому вона має бути короткою: **не більше 256 code
   points**. Ліміт однаковий для `--reason` і для `--topic-for`, і рахується
   в **code points**, а не в байтах — кириличний текст займає у rectifier
   вдвічі більше байтів, тож читач, який припустив байти, помилиться удвічі.
   `resolved.json` тримає ці рядки обмеженими за розміром (D-04), тому довге
   пояснення відхиляється, а не обрізається: обрізана підстава — це
   брехливий запис.

   Практична межа: одне речення на проєкт. Повний приклад:

   ```
   --reason "cs: ChatGPT is the only candidate above the 1000 views/month
   floor (1741). en: AI agent is the highest-volume candidate (35564)."
   ```

   `reason length = 183` — в межах. Якщо підтвердження відхилено з
   `must be bounded and control-free`, це означає рівно одне: текст довший за
   256 code points. Скоротить його, а не шукайте іншу помилку.
5. **Підтвердити можна тільки те, що discovery вже запропонував** (правило
   candidate-bounded). Слаг, якого немає серед збережених придатних кандидатів,
   буде відхилено, а не тихо створено.

Спроба підтвердити те, чого немає серед кандидатів:

```
resolver confirmation failed:
- selection is not one exact saved candidate: pl.wikipedia=Post_przerywany
```

Код `2`. `Post_przerywany` не існує в pl.wikipedia — резолвер не створює
статті, якої немає.

### Як зрозуміти, що підтвердження вдалося

У `out/resolved.json` мають змінитися три речі:

```json
{
  "run_mode": "confirm",
  "status": "confirmed",
  "projects": [
    {
      "project": "pl.wikipedia",
      "status": "ready",
      "selection": {
        "article": "G%C5%82od%C3%B3wka_lecznicza",
        "title": "Głodówka lecznicza",
        "reason": null,
        "source": "model_confirmation"
      }
    }
  ]
}
```

- `status` на верхньому рівні — **`"confirmed"`**
- `run_mode` — **`"confirm"`**
- у кожного запитаного проєкту `selection` заповнено

Код виходу `0`.

**Поки `status != "confirmed"` — не запускайте fetch і не пишіть `spec.json`.**
Підтвердження — це єдина гарантія, що вимірюватиметься саме те, що ви
погодилися.

### Коди виходу резолвера

| Код | Маніфест | Що робити |
|---|---|---|
| `0` | `awaiting_confirmation` (дискавері) або `confirmed` (підтвердження) | читайте далі або переходьте до `spec.json` |
| `2` | `unresolved`, або некоректне підтвердження | виправте запит або вибір; байти попереднього маніфесту збережені |
| `3` | `partial_error` | частина розділів впала, решта готова; роздивіться `error` у проблемному проєкті |
| `1` | `error` / нічого не записано | усі розділи впали, або фатальна 403/UA/помилка; читайте stderr |

`unresolved` домінує над `partial_error`: невирішена стаття важливіша за
часткову помилку. Якщо хоч один проєкт не розв'язано, увесь запуск повертає
`2`, і підтвердити такий маніфест неможливо.

> **Не редагуйте `resolved.json` руками.** Підтвердження валідується, і
> будь-яка правка руйнує документ. Потрібно щось змінити — запустіть
> discovery з новими аргументами.

## 12. Крок 5. Написання `spec.json`

Тепер і лише тепер пишемо вхідний контракт. Діє принцип **articles-first**:
тема живе тільки в `request` та `assumptions`, а в `series[]` — тільки
конкретні статті. Причина практична: `article` іде в URL AQS, і якщо дозволити
там тему, виробництво почне вигадувати слаги, які дадуть 404.

### Обов'язкові поля

Рівень кореня:

| Поле | Обов'язкове | Що це |
|---|---|---|
| `name` | так | ідентифікатор дослідження; копіюється в `metrics.json` як `spec_name` |
| `request` | так | запит користувача в оригінальних словах |
| `language` | так | мова **документа звіту** (`"uk"`, `"en"`), не мова даних |
| `window` | так | спільне вікно аналізу, однакове для всіх серій |
| `series` | так | непорожній масив конкретних статей |
| `assumptions` | ні | припущення, які користувач побачить у звіті |
| `quality` | ні | `{"fail_on_empty_series": true}` |

`window`:

| Поле | Обов'язкове | Формат |
|---|---|---|
| `start` | так | `YYYYMMDD`, без дефісів (напр. `20240923`) |
| `end` | так | `YYYYMMDD`, і `start < end` |
| `granularity` | ні | лише `"daily"` у v1 |

Кожен елемент `series[]` — усі п'ять полів обов'язкові:

| Поле | Що це | Часті помилки |
|---|---|---|
| `id` | стабільний ідентифікатор серії | має бути `[A-Za-z0-9._-]+`, інакше стадія charts відмовить |
| `project` | код розділу | `pl.wikipedia`, а не `pl.wikipedia.org` і не `https://…` |
| `article` | slug статті з підкресленнями | **percent-encoded** дослівно з `resolved.json`; ніколи не кодуйте повторно |
| `label` | людська назва для звіту й осі графіка | не впливає на дані |
| `language` | код мови статті | `pl`, `cs`, `uk` — мова **даних**, не звіту |

**Невідомі поля відхиляються, а не ігноруються.** Контракт заморожений: не
можна додати поле «на льоду», навіть якщо воно здається корисним.

### Готовий приклад

```json
{
  "name": "intermittent_fasting_pl_cs",
  "request": "Порівняй зростання інтересу до інтервального голодування в польськомовній і чеськомовній Wikipedia за останні два роки.",
  "language": "uk",
  "window": { "start": "20240923", "end": "20260920", "granularity": "daily" },
  "assumptions": [
    "у pl.wikipedia немає окремої статті про інтервальне голодування. Пошук за post przerywany / głodzenie przerywane / głodówka przerywana / przerywany / 16:8 не повертає відповідної статті, а Action API повідомляє missing для Post_przerywany, Głodzenie_przerywane, Głodówka_przerywana, Post_przerywany_(dieta). Найближча наявна стаття — Głodówka_lecznicza, і вона описує голодування загалом (у т.ч. лікувальне), а не інтервальний розклад",
    "дві серії вимірюють НЕ строго однакову тему: cs.wikipedia/Přerušovaný půst — окрема стаття саме про інтервальне голодування, тоді як pl.wikipedia/Głodówka lecznicza — про голодування загалом. Порівняння вимірює інтерес до суміжних тем, а не до одного й того самого розкладу",
    "обидва слаги відтворюють те, що видає resolve_articles.py (percent-encoded, safe=\"\"), і передаються у AQS URL без жодного перекодування",
    "обидві серії нижчі за поріг шуму 1000 переглядів на місяць, тому результат низької впевненості є очікуваним і не є виправом специфікації"
  ],
  "series": [
    {
      "id": "pl-post-przerywany",
      "project": "pl.wikipedia",
      "article": "G%C5%82od%C3%B3wka_lecznicza",
      "label": "Польська: голодування загалом (найближча наявна стаття, не інтервальне)",
      "language": "pl"
    },
    {
      "id": "cs-pust-prerusovany",
      "project": "cs.wikipedia",
      "article": "P%C5%99eru%C5%A1ovan%C3%BD_p%C5%AFst",
      "label": "Чеська: інтервальне голодування",
      "language": "cs"
    }
  ],
  "quality": { "fail_on_empty_series": true }
}
```

### Що робити з `request`

Пишіть **дослівний** запит користувача. Не переписуйте його під можливості
даних. Поле `request` — це голос користувача; застереження про те, що насправді
вдалося виміряти, живе в `assumptions` і потрапляє у звіт окремим розділом
«Обмеження та припущення».

Так само працює `label`: якщо серія вимірює суміжну тему, кажіть це в
назві («Польська: голодування загалом (найближча наявна стаття, не
інтервальне)»), а не приховуйте у примітці наприкінці.

### Про вікно

- `end` автоматично притискається до **останнього повного UTC-дня**. Запит за
  сьогоднішнім або майбутнім днем не створює нульових днів — вони просто не
  існують. Тому ставити «сьогодні» безпечно.
- Вікно довше за рік ділиться на chunk'и по ≤ 365 днів.
- **Зростання за 2 роки (`y2`) вимагає 730 днів поточного вікна плюс 730 днів
  базового** — тобто реально 1460 днів даних. На вікні 728 днів `2Y` завжди
  буде `н/д`, і це правильно, а не збій. Якщо вам потрібне `2Y`, замовте
  вікно від ~1460 днів.

## 13. Крок 6. Запуск пайплайну

Одна команда:

```bash
python scripts/run_all.py --spec out/spec.json --out out
```

Прапорці всього три: `--spec` (обов'язковий), `--out` (за замовчуванням `out`),
`--verbose` (діагностичні логи).

### Що відбувається всередині

Чотири стадії викликаються **послідовно, в одному процесі**:

| № | Стадія | Скрипт | Читає | Пише |
|---|---|---|---|---|
| 1 | fetch | `fetch_pageviews.py` | вікно і список статей зі spec | `series.csv` |
| 2 | analyze | `analyze_trends.py` | `series.csv` | `metrics.json` |
| 3 | charts | `make_charts.py` | `series.csv`, `metrics.json` | `charts.json` + PNG |
| 4 | report | `build_report.py` | `metrics.json`, `charts.json` | `report.md`, `report.manifest.json` |

Оркестратор зупиняється на **першій** ненульовій стадії, друкує в stderr
`run_all: stage <name> failed: …` і повертає код без змін. Жоден наступний
артефакт не пишеться — тому в `out/` ніколи не лежить набір файлів, що
напіввідповідає один одному.

`run_all.py` **не передає** `--log-scale` стадії charts, тому одна команда
завжди дає лінійний режим осі. Логарифмічний — це свідомий другий запуск
стадії charts напряму.

### Коди виходу

| Код | Значення | Що робити |
|---|---|---|
| `0` | усі чотири стадії успішні | читайте `metrics.json`, `report.md`, `charts.json` |
| `2` | **некоректний spec** | виправте spec за розділом 12 і перезапустіть; stderr перелічує **всі** порушення одразу |
| `1` | fatal: порожня серія, немає chunk'ів для завантаження, нечитаний вхід, відмовлена мова звіту, відсутній `WTI_USER_AGENT` | прочитайте stderr; виправте slug, вікно, `quality` або `WTI_USER_AGENT` |
| `3` | частково: ≥1 серія не завантажилась, ≥1 вдалась | прочитайте рядки `<series_id>: <message>`, виправте цей slug, перезапустіть |
| інше | аварія | повідомте дослівно; **не переписуйте логіку пайплайну** |

**Код `2` означає «виправ spec», а не «полаг код».** Він може прийти тільки з
валідації spec — жодна стадія не повертає `2` своїм результатом. Тому «spec
некоректний» і «щось зламалося» фізично не можна сплутати.

Валідація **агрегована**: перевіряються всі поля, і всі порушення повертаються
разом, а не по одному:

```
spec.json validation failed (3 errors):
- root.quality: expected an object (how to fix: use `{"fail_on_empty_series": true}`)
- series[0].label: missing required field (how to fix: add "label" like "Польська: інтервальне голодування")
- window: start (20260920) must be before end (20240923) (how to fix: swap so start < end)
```

Формат кожного рядка: `{шлях}: {проблема} (how to fix: {виправлення})`.

### Діагностичний шлях — стадії окремо

Коли одну стадію треба перезапустити з іншими опціями або потрібна її власна
діагностика в stderr, запускайте її напряму з тими самими `--spec` і `--out`:

```bash
python scripts/fetch_pageviews.py --spec out/spec.json --out out   # -> series.csv
python scripts/analyze_trends.py --spec out/spec.json --out out   # -> metrics.json
python scripts/make_charts.py  --spec out/spec.json --out out      # -> PNG + charts.json
python scripts/build_report.py --spec out/spec.json --out out     # -> report.md + report.manifest.json
```

### `metrics.json` — головний файл

Усі числа, які ви цитуватимете, беруться звідси. Формат:

```json
{
  "spec_name": "intermittent_fasting_pl_cs",
  "as_of": "2026-09-20",
  "generated_from": "out/spec.json",
  "series": [
    {
      "series_id": "pl-post-przerywany",
      "project": "pl.wikipedia",
      "article": "G%C5%82od%C3%B3wka_lecznicza",
      "label": "Польська: голодування загалом (найближча наявна стаття, не інтервальне)",
      "language": "pl",
      "total_views": 5814,
      "avg_daily_views": 8.0,
      "period": { "start": "2024-09-23", "end": "2026-09-20", "days": 728 },
      "growth": { "m3": { ... }, "y1": { ... }, "y2": { ... } },
      "anomaly_share": 0.017881705639614855,
      "trend_direction": "noise",
      "confidence": "low",
      "confidence_reasons": [
        "period at least 91 days",
        "monthly 30-day views below 1000",

      ],

```

Три поля, без яких відповідь неповна:

- **`as_of`** — дата останнього повного дня даних. Ставте її вголос.
- **`confidence`** + **`confidence_reasons`** — рівень впевненості і його

- **`trend_direction`** — напрям, який обчислив аналізатор. Значення
  `inconclusive` і `noise` — це **відповіді**, а не збої.

**У `metrics.json` немає жодного міжсерійного підсумку** — ні totals, ні
рейтингу, ні «загального зростання». Кожна серія описана окремо. Якщо вам
потрібне порівняння, порівнюйте серії між собою, а не шукайте в JSON
підсумкове поле.

## 15. Крок 8. Формулювання відповіді

Це найважливіший крок для чесності результату. Відповідь пишеться з
`metrics.json`, а не з власних обчислень.

### Правила

1. **Цитуйте `clean`-відсоток, ніколи `raw`.** `raw` містить спайк, який `clean`
   прибрав. Друкувати обидва означає зробити виключену аномалію частиною
   висновку. `report.md` показує тільки `clean`, і так само має робити ви.
2. **Завжди ставте базу обсягу поруч із відсотком.** `+5.7%` на 2363.5
   переглядів/день і `+5.7%` на 13 переглядів/день — це два різні факти під
   одним числом, і лише один переживає поріг шуму.
3. **`pct: null` — це «не обчислюється», ніколи `0`.** Не пишіть `0`, `0%`,
   `0.0`, тире і не залишайте клітинку порожньою. У звіті це локалізований
   токен `н/д` з причиною поруч.
4. **`trend_direction` — це значення, а не переказ.** Не пишіть «інтерес зростає»,
   якщо значення `up`. `up` означає: сирі й очищені читання **agree** за
   напрямом, і всі гейти пройдені. Це твердження про два вікна, а не про світ.
5. **`inconclusive` і `noise` повідомляйте як знахідки.** «Напрям за це вікно
   невизначений» — правдиве речення. Мовчки викинути серію — ні.
6. **Низька впевненість — це гіпотеза.** Формулюйте з hedge, нею,
   вкажіть рівень і причини, і не робіть з неї висновок.
7. **Скажіть вголос, що це не прогноз і не попит.**

### BEFORE / AFTER

| Не пишіть | Пишіть |
|---|---|
| Інтерес до інтервального голодування зростає на 5,7%. | За чистим 1R інтерес у польській Вікіпедії +5,7% на базі 2363,5 переглядів/день; впевненість низька, тож це гіпотеза, а не висновок. |
| Тема втрачає популярність. | За чистим 1R інтерес у чеській Вікіпедії −3,1% на базі 412,0 переглядів/день; впевненість низька через 8% аномалій — напрям не стійкий. |
| Дані ненадійні, краще не робити висновків. | Впевненість низька: період 60 днів коротший за 91 день, перегляди за 30 днів 210, нижче порогу 1000. Це твердження про коротке вікно, а не тренд. |
| Упередження interesting зростає на 400% — отже, тема на підйомі. | На 9 переглядів/день `+400%` — це 45 переглядів/день; впевненість низька, напрям `noise`, значення не проходить поріг шуму 1000 на місяць. |

### Мінімальний шаблон відповіді

```
Дані станом на <as_of>.

<назва серії>: <clean 1Y відсоток>% на базі <avg_daily_views> переглядів/день.
Напрям: <trend_direction>. Впевненість: <confidence> — <confidence_reasons>.
Частка аномалій: <anomaly_share>.

Припущення: <з assumptions, які стосуються цього висновку>.

Це не прогноз і не рекомендація: інтерес до статті — це не попит і не здатність платити.
```

# Частина IV. Довідники

## 16. Довідник `metrics.json`

### Вікна зростання

Три вікна однакової довжини, кожне закінчується на останньому повному дні
даних: `m3` — 91 день, `y1` — 365 днів, `y2` — 730 днів.

| Поле | Тип | Що це |
|---|---|---|
| `pct` | число \| `null` | відносна зміна до попереднього вікна тієї ж довжини |
| `abs` | ціле \| `null` | абсолютна зміна |
| `start`, `end` | дата | межі вікна |
| `clean.pct`, `clean.abs` | число \| `null` | те саме без аномальних днів |
| `reason` | рядок | **лише коли `pct` = `null`** |

```json
"m3": {
  "pct": 12.3, "abs": 1,
  "start": "2026-06-22", "end": "2026-09-20",
  "clean": { "pct": 9.1, "abs": 0 }
},
"y1": {
  "pct": -37.5, "abs": -4,
  "start": "2025-09-21", "end": "2026-09-20",
  "clean": { "pct": -38.5, "abs": -4 }
},
"y2": {
  "pct": null, "abs": null,
  "start": "2024-09-21", "end": "2026-09-20",
  "clean": {
    "pct": null, "abs": null,
    "reason": "insufficient observations in one or both equal-length windows"
  },
  "reason": "insufficient observations in one or both equal-length windows"
}
```

Тут видно три речі:

- `m3`: raw `12.3%` проти clean `9.1%` — аномалія з'їла три відсоткові пункти.
  У звіті буде `9.1%`.
- `y1`: напрям падіння стійкий (−37.5% і −38.5% в одній смузі).
- `y2`: `null` з причиною. Не `0`.

**Дві причини `null`, і тільки дві:**

| Причина | Що це означає |
|---|---|
| `insufficient observations in one or both equal-length windows` | в одному або обох однакових за довжиною вікнах бракує днів. Для `y2` потрібні 730 днів **плюс** 730 днів бази. |
| `previous equal-length window has zero mean` | середнє базового вікна рівно нулю, а відсоток математично невизначений |

### Рівень впевненості

`confidence` — **не почуття і не судження моделі**. Це результат цілочисельної
рубрики, і її можна відтворити з `confidence_reasons`:

| Терм | Умова | Бали |
|---|---|---|
| Період | `≥ 730` днів | +2 |
| Період | `91…729` днів | +1 |
| Період | `< 91` дня | 0 |
| Обсяг | 30-дн. середнє `≥ 10000` | +2 |
| Обсяг | `1000…10000` | +1 |
| Обсяг | `< 1000` | 0 |
| Аномалії | `anomaly_share == 0` | +1 |
| Аномалії | `0 < share ≤ 0.05` | 0 |
| Аномалії | `share > 0.05` | 0 |
| Методологія | вікно перетинає 2015-05-01 | **−2** |
| Розкриття | `clean` 1Y недоступний | 0 |

Смуги: `≥ 4` → `high`; `2…3` → `medium`; `< 2` → `low`. Серія з `low` додатково
отримує причину `low confidence: treat the reading as a hypothesis`.

Три речі, які варто знати перед цитуванням:

1. **`clean 1-year growth unavailable` не коштує балів.** Це розкриття, а не
   штраф: аналізатор каже, що очищене 1Y-порівняння обчислити не вдалося, і
   ви маєте сказати про це вголос, а не мовчки відкотитися на raw.
2. **Не відновлюйте рівень за кількістю reasons.** Список reasons може бути
   довшим за кількість термів. Рахуйте бали або цитуйте вже виданий рівень.
3. **Штраф за 2015 — єдиний від'ємний терм.** Двохрідна, високообсягова
   серія без аномалій може бути `low` виключно через перетин 2015. Скажіть
   про це прямо.

### Напрям тренду

П'ять значень: `up`, `down`, `flat`, `noise`, `inconclusive`. Вони
застосовуються в такому порядку:

| Умова | Результат |
|---|---|
| період `< 91` дня або `clean` 1Y = `null` | `inconclusive` |
| `confidence == "low"` або 30-дн. середнє `< 1000` | `noise` |
| `raw` 1Y і `clean` 1Y у **різних** смугах ±10% | `noise` |
| інакше | смуга `clean`: `up` вище +10%, `down` нижче −10%, `flat` між |

Третій гейт — серцевина. Один спайк здатний перевернути знак, і `clean`
існує саме для того, щоб це показати.

### Сезонність

`seasonality.months` — список місяців 1–12, у яких знайдено повторювані
піки. Він заповнюється **лише** за наявності двох вирівняних 365-дневних
напівперіодів. `seasonality.note` пояснює, що саме вдалося або не вдалося
виявити; цитуйте його дослівно, а не переказуйте як «сезонне / не сезонне».

| `note` | Що означає |
|---|---|
| `fewer than two aligned 365-day halves are available` | вікно закоротке для порівняння — твердження про сезонність не робиться взагалі |
| `no recurring peak months identified` | два напівперіоди є, але жоден місячний ефект не витримав перевірки |
| довгий `recurring peaks have positive shared month effects…` | піки знайдено, і цей текст точно каже, скільки ваги вони несуть: два цикли не відділяють сезонний ефект від календарної кривизни |

### Аномалії

```json
"anomalies": [ { "date": "2024-10-27", "value": 17, "median": 6 } ]
```

Аномалії виявляються **до** обчислення зростання, тому `clean` існує для
кожного вікна. Метод: ковзна медіана + масштабований MAD (радіус ±3 дні,
коефіцієнт 1.4826, поріг k = 3.5). Провали і спайки не розрізняються — у
записі просто `value < median`.

Аномалія — це запис у `anomalies[]`, **а не тренд**. Якщо один великий спайк
тягне весь тренд, це видно саме тут.

## 17. Довідник змінних середовища

| Змінна | Обов'язкова | За замовчуванням | Що означає |
|---|---|---|---|
| `WTI_USER_AGENT` | **так**, до будь-якого мережевого виклику | placeholder, який **відхиляється** | описова ідентифікація; ≤ 256 кодових точок, не placeholder |
| `WTI_CACHE` | ні | `.cache` | каталог кешу; створюється за потреби |
| `WTI_TTL_HOURS` | ні | `24` | свіжість кешу в годинах; `0` примусово робить запит |

Жодного API-ключа, токена чи акаунта. Єдиний «обліковий запис» навички — це
спосіб зв'язатися з людиною, яка відповідає за трафік.

### Як працює кеш

- Ключ — **SHA-256 повного URL**; файл `<key>.json`.
- Конверт — рівно `{fetched_at, status: 200, response}`.
- Пишеться **тільки перевірений HTTP 200**. Конверт, що не пройшов валідацію
  (не той status, немає `fetched_at`, `items` не список), **видаляється**, а
  запит повторюється.
- Кеш — головна причина, чому повторне або уточнювальне питання коштує нуль
  додаткових запитів.

## 18. Коди проєктів Вікіпедії

Код проєкту — це **хост-стем** Wikimedia Site Matrix, а не хост і не URL.

| Endpoint | Як виглядає код | Приклад |
|---|---|---|
| Action API (резолвер) | стем + `.org` як хост | `https://en.wikipedia.org/w/api.php` |
| AQS Pageviews (fetch) | стем як сегмент шляху | `https://wikimedia.org/api/rest_v1/metrics/pageviews/per-article/en.wikipedia/…` |

**Ніколи не пишіть `.org` і не пишіть URL у поле `project`.** Повний
каталог — `assets/wikipedia-projects.json` (`wikipedia-projects.v1`, 364 коди),
і він валідується точним збігом **до** побудови будь-якого URL.

Кілька поширених:

| Мова | Код |
|---|---|
| Англійська | `en.wikipedia` |
| Українська | `uk.wikipedia` |
| Польська | `pl.wikipedia` |
| Чеська | `cs.wikipedia` |
| Німецька | `de.wikipedia` |

## 19. Дозволені мови звіту

Поле `language` у `spec.json` — це мова **документа звіту**, а не мова даних.

| Мова | Графіки | Звіт | Підсумок |
|---|---|---|---|
| `uk` | так | так | **працює** |
| `en` | так | так | **працює** |
| `ja` | так | **ні** | графіки створяться, звіт відхиляється (див. нижче) |

Звіт пишеться **лише** словами, які є у власних словниках токенів, і мову, для
якої словника немає, **відхиляє** замість того, щоб підставити англійську.
Англійська — це не запасний варіант: український звіт з одним англійським
заголовком — це двомовний артефакт, якого читач не просив, і жодна перевірка
арифметики його не помітила. Числа були б усі правильні.

**Асиметрія `ja` — це не зламаний запуск.** Стадія charts приймає більше мов,
ніж стадія report. Специфікація з `language: "ja"` дасть валідний
`charts.json`, а потім буде відхилена на стадії report з кодом `1` і **без
записаного файлу**. `run_all.py` свідомо не вважає успіх стадії charts
передумовою для report.

Правильна реакція: прочитайте рядок у stderr, який називає мову, і поставте в
`spec.json` `uk` або `en`. Це обмеження покриття мов, а не збій.

Щоб додати мову, потрібні записи у п'яти словниках: `REPORT_TOKENS`,
`REASON_TOKENS`, `CONFIDENCE_TOKEN_KEYS`, `TREND_TOKEN_KEYS` у
`scripts/build_report.py` і `CHART_TOKENS` у `scripts/make_charts.py`.
Часткова добавлення — це відмова, а не запасний шлях.

## 21. Приклад B. Кейс низької впевненості

### B.1 Що сталося

Обидві серії в прикладі A дали `low` confidence і `noise`. Це **правильна
відповідь**, а не збій пайплайну.

### B.2 Чому

8.0 і 9.2 переглядів/день — це приблизно 215 і 248 переглядів на місяць, тобто
**далеко нижче порогу шуму в 1000 на місяць**. Аналізатор зобов'язаний повернути
`noise`, і саме це він зробив:

1. `confidence` — низька. Рубрика набрала 1 бал за період (728 днів ≥ 91) і
   0 за обсяг (менше 1000), 0 за аномалії (частка в межах 5%, але не нульова)
   → 1 < 2 → `low`.
2. `trend_direction` — `noise`, бо `confidence == "low"`. Гейт спрацював
   **раніше** за аналіз відсотків: напрям визначається з впевненості, а не
   зі знака відсотка.
3. Другий гейт (`30-дн. середнє < 1000`) дав би той самий результат навіть за
   вищої впевненості.

### B.3 Чому не треба цитувати відсотки

`-38.5%` і `-44.5%` за рік — це те, що робить серія з трьома переглядами на
день, коли один популярний тиждень переїжджає через межу вікна. За тиждень до
межі — 21 перегляд, тиждень після — 3. Відносна зміна на такому знаменнику
математично коректна і практично беззмістовна.

Це не падіння інтересу до голодування. Правильна відповідь каже, що **сигналу
немає**, а не що сигнал від'ємний.

### B.4 Правильне і неправильне формулювання

| Неправильно | Правильно |
|---|---|
| Інтерес до інтервального голодування в Польщі впав на 38,5%. | За чистим 1R інтерес у польській Вікіпедії −38,5% на базі 8,0 переглядів/день; впевненість низька (поріг шуму — 1000 на місяць), напрям `шум`, тому це гіпотеза, а не висновок про падіння. |
| Чеський ринок інтервального голодування звужується. | Чеська серія не дає висновку: 9,2 переглядів/день — це 248 на місяць, нижче порогу шуму. Значення −44,5% за 1R показані лише щоб було видно, чому їх не можна цитувати. |
| Дані ненадійні. | Впевненість низька: 215 і 248 переглядів за 30 днів, нижче порогу 1000. Це твердження про малий обсяг, а не про тренд. |
| Обидві мови втрачають популярність. | Жодна з двох серій не дає висновку про напрям — обидві повертають `шум`. |

### B.5 Як виглядає гіпотеза за правилами

Гіпотеза формулюється з hedge, несе свій рівень впевненості і свої причини, і
**ніколи не стає першим реченням відповіді**:

- ❌ «Польща: −38,5%»
- ✅ «За чистим 1R інтерес у польській Вікіпедії −38,5% на базі 8,0
  переглядів/день; впевненість низька, тож це гіпотеза, а не висновок.»

Ці формулювання не стилістична порада, а правило, яке механічно перевіряється
валідатором (розділ 23, властивість `low_is_hypothesis`).

### B.6 Що робити далі

Три варіанти, усі чесні:

1. **Змінити тему на ту, де обсяг є.** Інтерес до тем, що мають реальний
   обсяг, вимірюється. Поріг 1000 на місяць — не завада, а критерій якості
   даних.
2. **Залишити гіпотезу, але не робити з неї висновку.** Так теж правильно,
   якщо сказано вголос, що це гіпотеза.
3. **Змінити вікно на довше.** Два роки не допоможуть, якщо за добу приходить
   8 переглядів; допоможе лише інша тема чи інший розділ.

Що **не** варто робити: підміняти однеCPI тему іншою, вищою за обсягом, щоб
відсотки виглядали красиво. Тоді ви відповідаєте на інше питання, ніж те, яке
поставили.

## 23. Приклад D. Валідація відповіді моделі

Твердження навички просте: **дешева або безкоштовна модель може користуватися
нею, не вигадавши жодного числа.** Ось частина, яка це перевіряє.

### Команда

```bash
python tools/validate_answer.py --answer out/answer.md --out out
```

Де лежить файл відповіді: скрізь; `out/answer.md` — конвенція.

### Як отримати файл відповіді

1. Запустіть пайплайн (§13), отримайте `out/metrics.json` і `out/report.md`.
2. Дайте моделі ці два файли плюс інструкції з `SKILL.md` і
   `references/INTERPRETATION.md`.
3. Попросіть відповісти на питання користувача мовою користувача.
4. Збережіть відповідь у `out/answer.md`.

Модель має **читати, а не обчислювати**. Якщо вона виводить відсоток з
подвоєнням двох значень з `metrics.json` — це нове число, і це провал за
конструкцією.

### Чотири властивості

| Властивість | Що перевіряє |
|---|---|
| `numbers_present` | кожне число у відповіді присутнє в `metrics.json` цього запуску |
| `low_is_hypothesis` | серія з `low`-впевненістю сформульована як гіпотеза, а не як висновок |
| `as_of_present` | дата актуальності даних наведена в єдиному канонічному написанні |
| `sources_and_limitations` | обидва розділи присутні **і** мають непорожнє тіло |

### Читання вердикту

- Exit `0` — чотири рядки `PASS`.
- Exit `1` — хоча б один рядок `FAIL <property>: <detail>`, де `detail` називає
  число-порушник із номером рядка й зміщенням, або необережне речення.
- Exit `2` — проблема самого інструменту (файл не знайдено, не UTF-8,
  `metrics.json` не об'єкт), **ніколи** проблема відповіді.

Вивід також містить рядки `NOTE` для «вакуумних» перевірок — коли перевіряти
було нічого (наприклад, у `metrics.json` немає жодної `low`-серії). Вакуумний
результат проголошується явно, а не приховується мовчки.

### Приклад успішного запуску

```
PASS numbers_present
PASS low_is_hypothesis
PASS as_of_present
PASS sources_and_limitations
```

### Приклад провалу

```
FAIL numbers_present: answer number 41.8 at line 6 offset 12 is not in metrics.json
```

Тобто модель щось порахувала. Зазвичай це відсоток, виведений із двох
значень метрик.

### Що робити з кожним провалом

| Провал | Що означає | Що робити |
|---|---|---|
| `numbers_present` | модель щось обчислила | виправте промпт або `references/INTERPRETATION.md`. **Не послаблюйте перевірку.** Допуск «±epsilon» — це рівно те, що пропустило б неправильне число |
| `low_is_hypothesis` | помилка формулювання | процитуйте моделі пари BEFORE/AFTER з `references/INTERPRETATION.md` — вони існують саме для цього |
| `as_of_present` | промпт-пропуск | модель не сказала, наскільки свіжим є читання |
| `sources_and_limitations` | промпт-пропуск або порожній заголовок «для галочки» | те саме; порожній заголовок — це провал, а не прохід |

Кожен провал додатково пише **заготівку** в `out/eval/regression/` з
дігестом байтів відповіді, sha256 `metrics.json`, за яким її оцінювали,
порушеним токеном і версією валідатора. Справжній провал можна перенести в
`tests/fixtures/eval/` і закомітити — саме так збій стає регресійним тестом.

### Які моделі тестувати

Дешева модель — це і є потрібний тест: якщо навичка працює лише на дорогій,
вона не працює.

- **Claude Haiku 4.5** — нижній ярус фронтирної родини, найближчий спільний
  аналог «здатної моделі за бюджетом».
- **Безкоштовний тариф OpenRouter** — справжнє дно ринку і найчесніша
  перевірка того, чи інструкції навички несуть відповідь самотуж.

### Межа того, що тут постачається

Репозиторій постачає **валідатор і цей runbook, а не клієнт**. Живий запуск
дешевої моделі — крок власника репозиторію; жоден код тут його не виконує,
не тримає ключа і не ходить у мережу. В цьому сенсі оцінка закривається
частково **за задумом**, а не через забувливість.

# Частина VI. Довідка

## 24. Обмеження даних

П'ять підводних каменів. Кожен — що це, як виглядає в даних і чого читач не
повинен висновувати.

### 24.1 Розрив методології 2015-05-01

До **2015-05-01** Wikimedia фільтрувала павуків і ботів інакше, тому лічильники
по обидва боки цієї дати виробляє не один і той самий інструмент. Вікно, чиє
**порівняння** перетинає розрив, — це не порівняння «як з яким».

- **Як виглядає:** аналізатор виявляє перетин, віднімає **2** бали з
  впевненості й додає причину `comparison crosses 2015-05-01 methodology
  break`. Це єдиний від'ємний терм.
- **Чого не висновувати:** що серія до 2015 року — це тренд. Вікно
  2024–2026 повністю не зачеплене. Якщо ваші причини містять перетин, кажіть
  про це **в тому самому реченні**, що й відсоток, а не у зносці.

### 24.2 Поріг шуму низького обсягу

Нижче **1000 переглядів за 30 днів** читання — це шум, а не сигнал.

- **Як виглядає:** `trend_direction` примусово стає `noise` незалежно від
  відсотків, і рубрика не дає балів за обсяг (з'являється причина
  `monthly 30-day views below 1000`).
- **Чого не висновувати:** що `+400%` на 9 переглядів/день — це зростання.
  Це 45 переглядів/день, і про тему це не говорить нічого. Розділ 21.

### 24.3 Спайк проти зростання

Один вірусний день — це запис у `anomalies[]`, а не тренд.

- **Як виглядає:** аномалії виявляються ковзною медіаною з масштабованим MAD
  **до** обчислення вікон зростання, тому кожне вікно має варіант `clean` без
  аномальних днів.
- **Чого не висновувати:** що спайк є частиною тренду. **Цитуйте `clean`**;
  raw містить спайк, який ви зобов'язані дисконтувати, і друкувати обидва
  означає зробити виключену аномалію частиною висновку.

### 24.4 `null` і `unavailable` — це не нуль

У резолвері 404 дає `status: "unavailable"` з `total_views: null` і `null` у
`low_volume`. У метриках непідраховане вікно дає `pct: null` з `reason`.

- **Чого не висновувати:** що `0` і «не обчислюється» — це близько. Це різні
  твердження, і лише одне з них є фактом про світ. `0` читається як
  вимірювання: «виміряли — вийшло нуль». Насправді виміряти було неможливо —
  дані не опубліковані, вікно закоротке, або середнє базового вікна рівно нулю.

### 24.5 Обмеження шрифту CJK

Вбудований шрифт DejaVu покриває латиницю й кирилицю. Нелатинське письмо —
китайське, японське — рендериться **квадратиками-заглушками**, у stderr
з'являється одне попередження з назвою мови, а графік розкриває кількість
замаскованих точок. У v1 **резервного шрифту немає**. Це задокументований
розрив v1, а не помилка.

Пов'язаний факт — не про шрифт: стадія charts приймає більше мов, ніж report
(розділ 19).

### Межі, які жодне читання не переходить

- **Інтерес до статті — це не попит на продукт і не здатність платити.**
  Перегляди вимірюють увагу до статті Вікіпедії. Вони не вимірюють клієнтів,
  виручку чи намір купити.
- **Це опис виміряного минулого вікна, а не прогноз.** Кожне число описує дні,
  які вже завершилися. `trend_direction: "up"` — це твердження про порівняння
  двох вікон, а не проекція.

## 25. Обслуговування

### Повторний запуск того самого запиту

Просто запустіть `run_all.py` ще раз. Дані візьмуться з кешу (24 год за
замовчуванням) і жодного мережевого запиту не піде.

### Примусове оновлення даних

```bash
# разово, для пайплайну
WTI_TTL_HOURS=0 python scripts/run_all.py --spec out/spec.json --out out

# або для резолвера
python scripts/resolve_articles.py ... --ttl-hours 0
```

`0` вимикає читання кешу, але зберігає той самий ключ і той самий конверт
запису, тому наступний запуск знову буде читати кеш.

### Скидання кешу

```bash
# bash / zsh / macOS / Linux
rm -rf .cache

# PowerShell
Remove-Item -Recurse -Force .cache
```

Іншого механізму інвалідації немає, і на цій масштабі він не потрібен.

### Де тримати результати

`--out` — довільний каталог. Правило одне: **два незалежні процеси не повинні
писати в той самий `--out` одночасно.** Записи маніфестів атомарні (файл у
тому ж каталозі плюс один `os.replace`), але оркестратор не серіалізує два
процеси. Без серіалізації з боку викликача переможе **останній завершений
атомарний замінник**. Тому паралельні запуски в спільний каталог — не
прийнятно; дайте кожному свій `--out`.

### Помітка про застарілі артефакти

`charts.json` і `report.manifest.json` несуть `metrics_sha256` — дігест
`metrics.json`, який стадія прочитала. Порівняйте його з дігестом файлу, який
маєте у вас: якщо не збігається, маніфест описує інший стан даних. Це
**механізм цілісності, а не контроль доступу** — ним не можна будувати
авторизацію.

### Тести (якщо ви доробляєте навичку)

```bash
cd wikipedia-trend-agent
python -m pytest -q
python -m mypy scripts tools --strict
```

Тести не ходять у мережу: усі транспорти ін'єктовані або заборонені, а
фікстури — це реальні знімки API, збережені в репозиторії.

## 26. Швидка шпаргалка

### Мінімальний робочий сценарій

```bash
cd wikipedia-trend-agent

# 2. прочитати out/resolved.json і вибрати candidate.article для кожного проєкту

# 3. підтвердити (те саме, плюс --select; %-кодований slug)
python scripts/resolve_articles.py \

  --topic-for pl.wikipedia="głodówka przerywana" \

# 7. (опційно) перевірити свою відповідь

```

### Коди виходу `run_all.py`

| Код | Що це | Дія |
|---|---|---|
| `0` | успіх | читати `metrics.json`, `report.md` |
| `1` | fatal | читати stderr; виправити slug / вікно / `quality` / UA |
| `2` | **spec некоректний** | виправити spec; усі порушення вже в stderr |
| `3` | частково | прочитати `<series_id>: <message>`, виправити той slug |
| інше | аварія | повідомити дослівно, код не чіпати |

### Коди виходу `resolve_articles.py`

| Код | Маніфест | Дія |
|---|---|---|
| `0` | `awaiting_confirmation` або `confirmed` | далі або до `spec.json` |
| `2` | `unresolved` або некоректне підтвердження | виправити запит/вибір; попередні байти збережені |
| `3` | `partial_error` | розібрати `error` у проблемному проєкті |
| `1` | `error` | читати stderr |

### П'ять правил, які порушують найчастіше

1. `pct: null` — це **не обчислюється**, ніколи `0`.
2. Відсоток — ** завжди з базою обсягу поруч.
3. Цитуйте **`clean`**, ніколи `raw`.
4. `trend_direction` — це **значення**, а не «інтерес зростає».
5. `low` впевненість — це **гіпотеза**, а не висновок.

## 27. Як зробити PDF (необов'язково)

`report.pdf` — це **другий рендеринг того самого звіту**, а не другий звіт. Ті самі числа,
ті самі локалізовані рядки, інша лише верстка: таблиця на 11 колонок не вміщується в A4
(17,5 см корисної ширини), тому в PDF вона замінена **однією карткою на серію**.

За змовчуванням PDF **не** створюється. Жодного нового файлу, жодного нового рядка в
stdout, той самий код виходу.

### Встановлення

```bash
pip install -r requirements-pdf.txt
winget install Typst.Typst --silent --accept-package-agreements
```

`requirements.txt` **не змінюється** — це досі один рядок `matplotlib>=3.11`. PDF залежить
від двох речей, які користувач вмикає свідомо, і жодна з них не в базову інсталяцію.

### Запуск

```bash
# одразу в конвеєрі — пята стадія, після report
python scripts/run_all.py --spec out/spec.json --out out --pdf

# або окремо, як --log-scale: стадію можна викликати напряму
python scripts/build_pdf.py --spec out/spec.json --out out
```

Успіх: `out/report.pdf` і один доданий об'єкт у `formats[]` маніфесту
(`references/CONTRACTS.md` §8.1.1). `contract_version` лишається `report.v1` — додавання
елемента масиву **не** є бампом версії контракту.

### Діагностика відмов

| Повідомлення на stderr | Причина | Дія |
|---|---|---|
| `pypandoc is not installed` | немає опціонального пакету | `pip install -r requirements-pdf.txt` |
| `the typst binary was not found on PATH or under ...WinGet\Packages` | немає движка | `winget install Typst.Typst --silent --accept-package-agreements` |
| `none of the candidate font families is installed for typst (...)` | typst не має жодного зі шрифтів, які вміють кирилицю | встановіть Arial / Liberation Sans / Noto Sans, або сам typst |
| `could not fetch N image(s) and replaced each with its description` | графік відсутній у каталзі `--out` | перевірте, чи всі `chart_*.png` на місці. **PDF не опубліковано** — інакше читач отримав би звіт без доказів |
| `the produced PDF carries N image markers where M were expected` | те саме, або змінився внутрішній формат typst | перевірте файли; якщо файли на місці — гейт треба перевиміряти |
| `the manifest records metrics_sha256 ... but the metrics.json on disk hashes to ...` | звіт застарів | перезапустіть конвеєр **без** `--pdf`, потім з ним |
| `report.manifest.json is missing` | PDF-стадію запустили до `report` | спочатку `run_all.py` без `--pdf` |

Жодна з цих відмов **не залишає** файлу: публікація атомарна (тимчасовий файл + `os.replace`),
і попередній `report.pdf` залишається побайтово ідентичним.

### Що робити, якщо PDF не потрібен

Нічого. Без `--pdf` пайплайн поводиться точно так само, як до цієї функції — це перевірено
хешем кожного файлу у вихідному каталозі, а не на око.
